# capture-core

Screen and window capture for Kimochi: ScreenCaptureKit on macOS, Windows Graphics Capture on
Windows, and PipeWire portals or X11 on Linux, with crop validation, frame mapping and pixel conversion.
It began as a separate capture experiment by the same author. On macOS, display captures exclude
Kimochi's own windows (refreshed with each source catalog lookup), so the overlay and native
controls stay out of scans without being hidden.

## Persistent streams

`MacCapture` keeps each captured source running as an `SCStream` (at most two at once, each stopped after 30s without a capture) and answers later captures by copying the stream's newest frame. Measured on a 3456x2234 display: a one-shot capture cost ~110ms (53ms re-listing windows, 41ms `SCScreenshotManager`, 19ms `CGImage` redraw); a crop from the running stream costs ~1–2ms and a full frame ~4–8ms. Window streams read the window's live geometry from each frame and restart on resize. Thumbnails stay one-shot, scaled on the GPU via the stream configuration. The one-shot path is also the fallback when a stream produces nothing within 500ms.

`WgcCapture` (Windows, `windows-capture` 2.x) mirrors that shape: at most two retained Windows Graphics Capture sessions, LRU eviction, a 30s idle stop, a 500ms first-frame wait, and a latest-frame mailbox each capture copies from. Ids are `windows:window:{HWND hex}:{pid}` and `windows:display:{HMONITOR hex}`. Bounds are physical virtual-screen pixels (`DWMWA_EXTENDED_FRAME_BOUNDS`); window frames are cut to that visible rectangle, so the invisible resize borders never reach a crop. Cursor capture is off; the capture border is left at the system default because removing it needs the user's separate Borderless consent. Thumbnails come from one frame, box-filtered on the CPU. Untested on real Windows so far: it type-checks with `cargo check --target x86_64-pc-windows-msvc`.

`GamescopeCapture` (Steam Deck Gaming Mode, `src/linux_gamescope.rs`) reads Gamescope's own PipeWire node (`node.name = gamescope`) instead of the portal, chosen by `platform_backend()` when the session is Gamescope's XWayland overlay setup and the node is present (`linux_gamescope::available()`, one registry round trip per process). `enumerate()` lists `gamescope:display:0` and `gamescope:window:{appid}:{pid}` per running app from `GAMESCOPE_FOCUSABLE_APPS`/`GAMESCOPE_FOCUSABLE_WINDOWS` on `$DISPLAY` (Steam's client, app 769, and this process left out; names are window titles, often empty, for the app to replace). Capture asks for an app through Gamescope's private `focus_appid` format property (`0x70001`), which composes that app alone even when it is not in front; one stream is reconnected to switch apps (about 80 ms on a Deck), and the newest frame of each app is kept for thumbnails. Gamescope only sends a frame when the app draws. While another client is linked to the node (Steam's game recording) it never switches apps (`busy`). Checked on SteamOS 3.8.16 / Gamescope 3.16.23.4 with `examples/gamescope_sources.rs`.

`PortalCapture` (Linux Wayland, `src/linux_portal.rs`) is the xdg-desktop-portal ScreenCast portal (`ashpd` 0.13, on zbus's `async-io` runtime) plus a PipeWire stream (`pipewire` 0.10). It is a session, not an inventory: `capabilities()` reports `xdg-portal-pipewire`, no enumeration, `system_picker_required`, a retained session; `permission()` is `promptOnSelect` until a pick succeeds and `granted` while the session lives. `request_permission()` opens the system picker (single monitor or window, cursor hidden, persisted until revoked with the stored restore token) and blocks up to 120s, returning false on cancel, denial, a missing portal or timeout (`PortalCapture::last_error` says which); call it from a user gesture on a worker thread. `enumerate()` then lists only the shared stream as `portal:display:{node}` or `portal:window:{node}` ("Shared screen"/"Shared window"); monitors carry their compositor-logical bounds, windows none. A PipeWire thread negotiates BGRx/BGRA/RGBx/RGBA on SHM buffers only (no DMA-BUF), honours row stride and GNOME's `VideoCrop` region, and keeps the newest frame as RGBA in a mailbox; `capture()` waits at most 500ms for the first frame, `thumbnail()` box-filters it, and `scale_factor` is frame pixels per logical unit. A session revoked from the compositor or a closed source turns every capture into `stale_source` and `permission()` back to `promptOnSelect`. Restore tokens go through `set_portal_token_store(Box<dyn TokenStore>)` (in memory by default). Building it needs `libpipewire-0.3-dev`, `libspa-0.2-dev` and libclang (bindgen); from macOS it type-checks with `cargo check --target x86_64-unknown-linux-gnu` against Debian's headers extracted into a sysroot (`PKG_CONFIG_PATH` pointing at `.pc` files for them, `BINDGEN_EXTRA_CLANG_ARGS_x86_64_unknown_linux_gnu="--target=x86_64-unknown-linux-gnu --sysroot=…"`, the same in `CFLAGS_x86_64_unknown_linux_gnu`, `AR_x86_64_unknown_linux_gnu=ar`). Untested on a real Wayland session so far.
